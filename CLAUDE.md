# CLAUDE.md — LedgerLoop

## What this project is

Three-source settlement reconciliation for a Razorpay Buildathon submission (Track 04, AI Finance
Controller). Deadline 5 Sep 2026. Read `PROJECT_SPEC.md` before any architectural work — it is the
source of truth for design decisions, and those decisions are deliberate.

## Non-negotiable architectural rules

These are the thesis of the project. Do not "improve" them without asking.

1. **Deterministic tiers decide; the LLM only proposes evidence.** Tiers 0–2 must never call a model.
   If a match can be made by arithmetic or string normalisation, it is made by arithmetic.
2. **The LLM never overrides arithmetic.** Every tier-3 proposal is re-verified in Python against the
   fee model and date window. If the numbers disagree with the model, the numbers win.
3. **The LLM may only return IDs from the candidate set it was given.** Any ID outside that set means
   the whole response is discarded and an `LLM_INVALID_OUTPUT` exception is raised. No retry loops
   that coax out a parseable answer.
4. **Ambiguity is never resolved by guessing.** Two valid subset explanations → `AMBIGUOUS_SUBSET`
   exception, both explanations attached. Never pick the higher-scoring one.
5. **A false match is worse than an exception.** When in doubt, raise an exception. Optimising the
   headline match rate at the cost of precision is a bug, not a tradeoff.
6. **`eval/` is the only package permitted to import ground truth.** There is a test enforcing this.
   Never read `truth_links.csv` from `ledgerloop/`.
7. **Never hand-write a metric into README.md or results/.** Every number is generated by `make eval`.

## Conventions

- Python 3.11. All money is **integer paise**. Never float, never Decimal-in-storage. A float in a
  money path is a defect — flag it if you see one.
- Dates are `datetime.date`, timezone-naive, IST assumed. Business-day math goes through
  `ledgerloop/generate/fee_model.py::business_days_after`, never inline.
- Pydantic v2 for every boundary: file ingest and LLM output. Same tool, both edges.
- SQLite tables are append-only. Corrections are new rows, never UPDATEs. Provenance depends on this.
- Every posted match writes a `match_record` with: tier, rule_id, evidence JSON, SHA-256 fingerprints
  of the source rows, timestamp, and (tier 3 only) model name + prompt version.
- Exception reason codes live in `ledgerloop/exceptions/codes.py` as an enum. Do not invent string
  literals at call sites.
- Test names describe behaviour: `test_ambiguous_subset_raises_rather_than_matching`.

## Working style I want

- **Plan before writing.** For anything touching the cascade, propose the approach and wait for my
  go-ahead. I have to defend this architecture in a panel interview, so I need to understand every
  decision before it lands.
- **Tests first on money logic.** Fee model, tolerance bands, and subset-sum get failing tests before
  implementation. Use hypothesis for property tests on the fee arithmetic.
- **Small commits.** One tier, one concern. Do not refactor adjacent code while implementing a tier.
- **Explain tradeoffs, don't just pick.** If there are two reasonable approaches, say so and say why
  you'd pick one. Short is fine.
- **Push back on me.** If I ask for something that breaks a rule above, say so instead of complying.

## Deliberately excluded

Do not add these, and do not suggest them: LangChain, LlamaIndex, or any agent framework (the entire
LLM surface is one schema-constrained call — a framework here undercuts the project's argument);
vector databases (nothing to retrieve); Docker/Kubernetes (a Makefile is more honest for a single-file
SQLite app); ORMs beyond SQLAlchemy Core; fine-tuning; multi-currency; auth or user accounts.
